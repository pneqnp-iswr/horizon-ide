# Horizon IDE Runtime Contract v0.1 — Local Horizon client

The first IDE foundation includes an external-process game panel. This adapter hardens that experiment; it does **not** implement the final game host.

## User-facing behavior

1. The user selects an absolute path to an installed, trusted `horizon-client` or `horizon-client.exe`.
2. **Check Horizon** executes that binary with only `--launch-api` (no world starts) and accepts Launch API `0.x` from `0.1.0` if both `--game-dir` and `--home` are advertised. It times out after eight seconds and refuses oversized or malformed responses.
3. **Launch** performs that check again, asks for explicit user consent, creates a unique disposable game and home directory under the user's temporary folder, and invokes the selected client with only the internally generated `--game-dir` and `--home` flags. The app owns at most one process and does not select personal save paths.
4. Status comes from the OS child handle, refreshed every 1.5 s. `Running` means an OS process exists; it **does not** prove the game rendered, an item loaded or the mod executed.
5. **Stop** terminates and reaps only the child the IDE launched. Normal IDE shutdown also attempts to terminate it. The disposable session directory is removed after a clean stop or observed exit; a crash or forced process termination may leave it behind in the system temporary folder.

## Security / non-goals

- Names and protocol checks are compatibility signals, **not** a cryptographic trust proof. A malicious file named `horizon-client.exe` can execute code if the user selects it. Run only installations obtained through trusted channels.
- No executable text, flags or command lines generated by an AI provider are passed to the launcher.
- No launcher authentication, player tokens or personal Minecraft assets are accessed by the inspector.
- No screenshot from an offscreen game is mislabeled as a playable embedded viewport.
- Temporary game/home isolation prevents the IDE from deliberately opening the user's personal saves, but is **not** a security sandbox. A malicious game binary or full-trust native mod can still access arbitrary files available to the user.
- This is still an external process, not a verified in-game session or interactive embedded viewport. The full HS-023 Preview Bridge and actual mod-load assertions remain outstanding.
- There is no native `.hnmod` hot swap. Native source-mixin mods are compiled into the Horizon client, so this workflow will require a separately authorized build and restart.

## Verification levels

| Level | What it proves | Current status |
| --- | --- | --- |
| Unit | Compatibility parser refuses malformed/outdated data | Rust tests added |
| Process | Launched child is owned, exits are noticed, no duplicate launch | Rust unit + UI flow |
| Launch API | Selected local binary supports required interface | User-run preflight, no real Horizon test in CI |
| Real game-load | The running game confirmed package content | **Not tested** |
| Interactive embedded viewport | Game is playable in an IDE pane | **Not implemented** |
| Gameplay | Real in-world behavior follows the authored code | **Not tested** |

## Next milestone: external tool to real Preview Bridge

Port the proven Python `studio_core/preview_bridge.py` logic from Horizon Studio or implement an equivalent typed Rust adapter using upstream `horizon-ctl` (with tests against genuine and adversarial replies). Use a fresh disposable `--game-dir` and `--home`, explicit session consent, exact inventory delta checks, content SHA-256, engine build identity and captured validation artifacts.

Only after real game-load evidence should we attempt the separate HWND / upstream winit-wgpu embedding feasibility spike. A playable native viewport and hot content iteration remain **gated** on these results.
